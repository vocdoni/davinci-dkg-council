# October 2026 audit of Council v2

An internal audit of the complete v2 protocol stack, run in October 2026 right after the v2
merge (spec adopted 2026-10-06) and before any production deployment. Seven independent
reviews, one per part of the system; every finding below links the commit(s) on `main` that
carry its fix. **Headline result: no forgery, no composition hole and no exploitable cryptographic
or contract flaw was found.** Everything that was found is fixed in the commits listed here,
except the explicitly open items in the last-but-one section — of which the production
multi-party trusted setup remains the release blocker.

## Scope

Seven parts, each reviewed independently against the normative docs
([protocol.md](protocol.md), [architecture.md](architecture.md), [relayer.md](relayer.md)):

1. **Protocol and long-term security model** — the §-numbered protocol spec, key lifetimes,
   the recovery kit, decryption policies, and what six-month elections assume.
2. **Contracts and the DAVINCI registry** — CouncilManager + views + ops, the deployment
   scripts, and the davinci-contracts COUNCIL key mode integration.
3. **Circuits and v2 composition** — both Groth16 statements, the point codec, and how the
   verifier's public inputs are bound to contract storage.
4. **SDK and app** — `@vocdoni/davinci-dkg-council-sdk` and the browser app, including the
   restore/kit paths and local persistence.
5. **Relayer** — transaction sending, budgets, the scheduler, state persistence and the
   deployment scripts.
6. **Operations and product risk** — hosting, RPC policy, monitoring, organizer workflows,
   incident handling and docs honesty, all under the "election that opens months later" lens.
7. **Cross-implementation consistency** — every value that exists in more than one
   implementation (TS, Solidity, vendored ABIs, sibling DAVINCI repos).

## Method

- Each part was reviewed by an independent reviewer with no stake in the code under review;
  parts 1, 2, 4 and 5 by static adversarial code review against the spec, part 6 as an
  operational risk review, part 7 by mechanical cross-checking of every coupled constant,
  encoding and ABI (including re-running `make vectors` and diffing the SDK ABI against a
  fresh `forge build`).
- The circuits (part 3) were attacked, not just read: an adversarial reviewer enumerated every
  prover-controlled value, built tampered witnesses and encodings from honest ones, and ran
  them against the verifier — malformed codec words, swapped public inputs, off-subgroup and
  low-order points, hint manipulation. The accepted/rejected matrix became permanent negative
  tests (composition tests in `21451a6`, `CouncilCodec.t.sol` additions in `3ed3a3f`).
- Every accepted finding got a regression test with its fix; differential tests cover the
  cross-implementation surfaces (codec vectors, EIP-712 encodings, public-input layouts).

## Results

No critical finding anywhere. By part:

### 1. Protocol and long-term model (0 critical, 1 high, 2 medium, 2 low)

| ID | Severity | Finding | Fix |
|---|---|---|---|
| H-01 | High (release blocker) | The development trusted setup (`circuits-v1`) was deployable on production chains: nothing enforced the release's `DEVELOPMENT_SETUP` flag at deploy time, and nothing disclosed it to users. | `3ed3a3f`, `ca38b3e` (deploy refuses a dev release off the test chains), `00eeee4` (persistent in-app test-setup banner), `4ef038f` (SDK exposes the release trust status), `21451a6` (multi-party phase-2 ceremony tooling); the release pin now rewrites the SDK flag so the two cannot drift. **Running the production ceremony itself is still open — see below.** |
| M-01 | Medium | Pruned historical logs hid the member republication action: an RPC that refuses old log queries made the app conclude "nothing to republish" instead of offering the deterministic re-publication. | `4ef038f`, `00eeee4` — unavailable history is distinguished from authenticated absence; the UI offers republication and rebuilds the original committed vector. |
| M-02 | Medium | Relayer decryption service depended on historical logs: discovery failure blocked even already-known requests. | `6ce783a` (requests found from contract state via `getRequestCount`/`getRequestIdsPage`; logs demoted to a convenience; authenticated `POST /v1/track` endpoint + metrics alerts); the app now registers every committee it creates with the relayers via that endpoint. |

## What remains open, and why

- **The production multi-party trusted setup — the release blocker.** `circuits-v1` is a
  development phase 2: anyone holding its toxic waste could forge dealings and partials. The
  ceremony tooling exists (`circuits/scripts/ceremony/`, Hermez/PPoT phase 1, `21451a6`), the
  deploy script refuses the dev release on production chains (`3ed3a3f`, `ca38b3e`) and the app banners
  it (`00eeee4`), but the ceremony itself — independent contributors, published transcripts,
  re-pinned release, new manager — has not been run. Nothing before that gate is a real
  election. This is scheduling and coordination, not code.
- **Hosting and mirror execution (P0.3, P0.6).** The policy is written
  ([hosting.md](hosting.md)); standing up the app-independent permanent artifact mirror, the
  second hosted app copy and the versioned origins are provider decisions still to be made.
- **Incident governance roles.** [incident-response.md](incident-response.md) defines the
  playbook; who holds the roles it names (triage owner, relayer stop authority, the
  independent verifiers of an exceptional off-chain tally) is unassigned.
- **The DAVINCI coordinated redeploy and release order (P1.6).** The registry redeploy with
  the COUNCIL key mode must ship after the davinci-sdk major release that understands
  mode 3, then the sequencer (which also resyncs its ABIs, mirror #3/#4) — three external
  repos, one ordering constraint.
- **External-repo findings**: protocol L-02 (davinci-sdk nonce-reuse docs) and mirror #3/#4
  (davinci-sequencer), tracked in their repos.

## Long-term assumptions

The security argument for an election that opens months after key generation rests on
assumptions the protocol cannot enforce; the audit made them explicit and the docs now state
them ([protocol.md](protocol.md), [organizer-guide.md](organizer-guide.md)):

- **Compromise accumulates over the key's lifetime.** A threshold key is only as safe as the
  `t`-of-`n` custody of the member roots for the whole period; kits are plaintext roots, a
  root exposure spans every ceremony it joined, and a share refresh would not erase a past
  exposure.
- **Organizer liveness is load-bearing in Manual mode.** A disappeared organizer without a
  fallback date can block decryption forever; the manual fallback is a latest-opening bound,
  not a not-before.
- **Adapter grants are decryption oracles.** An organizer who approves an arbitrary adapter
  has authorized arbitrary decryption requests; grants are permanent and must be treated as
  key-custody decisions.
- **Independent privacy domains need separate ceremonies** (and separate roots for hard
  isolation).
- **Timestamp predicates are not alarms**: the contract enforces windows, nothing wakes
  anyone up — monitoring and the organizer calendar exist for that.
- **RPC unanimity can stall on one lagging provider**; the 365-day bound limits the dealing
  window only, not the key's life.
- **There is no pause and no upgrade.** The contracts are immutable by design; the only
  responses to a bug found mid-election are the incident playbook's: suspend client
  participation, an exceptional independently verified off-chain tally, or cancel and rerun.
